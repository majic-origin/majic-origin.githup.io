**### 前言**
做业务开发久了会发现，绝大多数难以维护、改一处崩一片的工程代码，根源都踩中了 SOLID 里最基础的两个坑：类职责混乱、新增需求就暴力修改原有逻辑。
单一职责（SRP）、开闭原则（OCP）作为面向对象设计的底层基石，也是所有设计模式的设计初衷。今天抛开教科书式冗长定义，结合「反例 - 问题拆解 - 重构优化」实战，一次性讲透落地思路。

### 一、单一职责原则：一个类只做一件事
1. 核心思想
高内聚，低耦合。一个类仅有一个引起它变化的原因。
直白翻译：如果一段业务逻辑里，这个类既要处理 A 逻辑，又要处理 B 逻辑，后续修改 A 时极易误伤 B，这就是职责过载。
反面示例：职责堆砌的臃肿类

```
public class AnimalService {
    // 同时承载发声、运动两套逻辑
    public void action(String animalType) {
        if ("dog".equals(animalType)) {
            System.out.println("狗：汪汪汪");
            System.out.println("狗：快速奔跑");
        } else if ("cat".equals(animalType)) {
            System.out.println("猫：喵喵喵");
            System.out.println("猫：缓步踱步");
        }
    }
}

```
现存痛点
功能耦合：只想复用发声逻辑，必须连带运动代码，无法拆分；
维护成本高：修改动物运动逻辑，需要改动本类，有概率影响发声逻辑；
扩展性差，类会随需求迭代持续膨胀。
重构方案：按职责拆分类
把发声、运动逻辑拆成两个独立类，各自只负责自身单一业务：

```

// 发声职责类
public class SoundService {
    public void makeSound(String animalType) {
        if ("dog".equals(animalType)) System.out.println("狗：汪汪汪");
        if ("cat".equals(animalType)) System.out.println("猫：喵喵喵");
    }
}

// 运动职责类
public class MoveService {
    public void move(String animalType) {
        if ("dog".equals(animalType)) System.out.println("狗：快速奔跑");
        if ("cat".equals(animalType)) System.out.println("猫：缓步踱步");
    }
}


```
重构收益
逻辑隔离，修改任意一方互不干扰；
按需复用，需要哪个功能就引入对应类；
代码可读性拉满，新人接手能快速看懂每个类定位。
**### 二、开闭原则：对扩展开放，对修改关闭**
1. 核心思想
系统功能迭代时，新增需求通过扩展实现，而非修改已稳定运行的旧代码。
旧代码经过测试、线上验证，随意修改会引入隐性 Bug；合理抽象后，新增逻辑只新增实现类，完全不动存量代码，这就是开闭原则的落地核心。
反面示例：硬编码 if 分支，新增需求必改旧代码
沿用上面发声逻辑，现在要新增鸟类，只能侵入原有方法新增 else if 分支：

```

public class SoundService {
    public void makeSound(String animalType) {
        if ("dog".equals(animalType)) {}
        else if ("cat".equals(animalType)) {}
        // 新增鸟类，强制修改原有稳定代码，违反开闭
        else if ("bird".equals(animalType)) {}
    }
}


```
现存痛点
存量代码反复改动，每次迭代都要回归测试原有逻辑，风险极高。
标准落地方案：抽象接口 + 多态扩展

抽象顶层接口（稳定层，全程不改动）
```
public interface Animal {
void makeSound();
}

```
已有动物实现类（存量代码，无需任何修改）
```
public class Dog implements Animal {
    @Override
    public void makeSound() {
        System.out.println("狗：汪汪汪");
    }
}

public class Cat implements Animal {
    @Override
    public void makeSound() {
        System.out.println("猫：喵喵喵");
    }
}

```
新增鸟类需求：仅新增实现类，零改动旧代码
```
public class Bird implements Animal {
    @Override
    public void makeSound() {
        System.out.println("鸟：叽叽喳喳");
    }
}
```

统一多态调用

```
public class Test {
    public static void main(String[] args) {
        Animal dog = new Dog();
        Animal cat = new Cat();
        Animal bird = new Bird();
        dog.makeSound();
        cat.makeSound();
        bird.makeSound();
    }
}
```

重构收益
存量代码零修改，线上稳定逻辑不受影响；
无限扩展，新增业务仅新增实现类，符合工程迭代规范；
完全依托多态实现，是框架、中间件通用设计思路。
### 三、两大原则协同关系
单一职责是代码分层的基础：先拆分职责，避免一个抽象承载过多逻辑；
开闭原则是迭代扩展的保障：在职责单一的基础上做抽象，实现无痛迭代。
简单总结：单一职责管「代码整洁度」，开闭原则管「项目生命周期」，二者结合才能写出易维护、易扩展的工程代码。
### 四、最后小结
很多同学写代码只追求功能跑通，忽略设计原则，短期开发速度快，但项目迭代三个月后，耦合、臃肿的代码会极大拖慢开发效率。
理解并落地单一职责、开闭原则，是从 “堆砌功能的面向过程写法” 进阶到 “规范面向对象开发” 的关键一步，后续学习所有设计模式，底层逻辑都离不开这两个核心规范。
